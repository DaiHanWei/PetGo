# 系统通知补做规格（V1.0.0 → V1.1.2 全量归集）

## 0. 文档说明

**为什么有这份文档：** 从 V1.0.0 到 V1.1.2，各版本 PRD 陆续定义了大量依赖「系统级推送通知」的行为，但工程侧一直未接入推送通道（无 FCM/APNs 集成、无设备 token 存储）。本文档把散落在 6 份文档里的通知需求**一次性归集**，作为补做的唯一输入口径，不新增需求。

**范围边界：**

| 纳入 | 不纳入 |
| --- | --- |
| V1.0.0 PRD §4.7 / §4.14（FR-22A/B/C/D/E、FR-34、FR-38、FR-40、FR-41、FR-42 L 级） | FR-85 推送权限多触发点唤醒（归 **V1.1.4**，见 `../V1.1.4/改版1-1-4prd.md` §2.8） |
| V1.1.0 PRD §3.8 / §3.9 / §3.12（FR-51、FR-52A、FR-52B、FR-22 系列重申、通知文案汇总表） | AB-11A 后台批量推送催填手机号（归 **V1.1.4**） |
| V1.1.0 审核方案 §8 全部通知文案（8.1~8.10） | 推送通知**分类开关**（V1.0.0 §6.2 明确排期 **1.4.0**） |
| V1.0.0/V1.1.0 后台 PRD 中触发通知的运营动作（AB-3C、AB-5B、AB-9B/9C） | 健康记录提醒推送（疫苗/驱虫间隔提醒，归 **1.3.0**） |
| 数据模型 `notifications` / `scheduled_push_marks` / `users.locale` | 兽医预约上线提醒（归 **1.3.0**） |
| V1.1.2 对通知的**间接影响**（Tab 改版 → 深链与铃铛入口） | 腾讯 IM 私聊消息本身的推送（另属 IM 通道，本文档不覆盖） |

**术语口径（下游必须统一使用）：**

| 术语 | 定义 |
| --- | --- |
| **系统级推送（Push）** | 经 FCM/APNs 投递到操作系统通知栏的消息，依赖用户授予推送权限。本次补做的主体。 |
| **站内通知（In-App Notification）** | 写入 `notifications` 表、在 App「通知中心」（FR-34）列表可见的条目。**不依赖权限**。 |
| **App 内提示（In-App Prompt）** | 版本更新弹窗（FR-22C）、Toast、Banner 等，**既不走推送也不写通知中心**。 |
| **双通道** | 同一事件同时写站内通知 + 发系统推送。**本产品绝大多数通知都是双通道**，权限未授权时仅保留站内通知。 |

## 1. 现状与缺口

### 1.1 已经有的

- `notifications` 表已建（16 个 type 枚举、标题/正文/深链/已读态齐全），**是通知中心的读取来源**
- `scheduled_push_marks` 表已建（生日/纪念日/里程碑三类定时推送的去重标记，`(pet_profile_id, push_kind, node_key)` 唯一）
- `users.locale` 字段已建（id/en，**明确注明「用于系统推送按用户语言渲染文案」**）
- 页面侧 P-09（通知权限请求弹窗）、P-13（通知中心页）已在 `V1.0.0/page-list.md` 登记

### 1.2 缺的（补做范围）

| # | 缺口 | 影响 |
| --- | --- | --- |
| G-1 | **无推送通道接入**（FCM/APNs SDK、证书/密钥、服务端投递服务） | 所有系统推送为空 |
| G-2 | **无设备 token 存储表** | DB schema 中无 device/push token 表，无法定向投递 |
| G-3 | **推送权限申请未落地**（FR-22D 推送部分、P-09 页面） | 即使接通道也无授权 |
| G-4 | **深链路由表未落地**（FR-38 冷启动/后台/前台三态） | 点通知无法直达目标页 |
| G-5 | **定时扫描任务未落地**（生日/纪念日/里程碑每日扫描 + 去重查表） | `scheduled_push_marks` 表建了但无写入方 |
| G-6 | **多个已定义通知在 DB 枚举中无对应 type**（见 §9.2） | 审核治理类通知发不出去 |
| G-7 | **无推送相关埋点**（`埋点清单v112.md` 中不存在推送送达/点击/权限授权事件） | 无法评估补做效果 |
| G-8 | **兽医端推送通道缺失**（FR-22E，兽医端无通知中心，只能走离线推送） | 抢单模式无法运转 |

## 2. 通知能力三层结构

```
事件发生
   │
   ├─→ 写 notifications 表 ──→ 通知中心 FR-34（铃铛 + 未读角标）  ← 不依赖权限，必做
   │
   └─→ 系统推送 FCM/APNs ──→ 通知栏横幅                          ← 依赖 FR-22D 权限
                                    │
                                    └─→ 点击 → 深链 FR-38 → 目标页 → 同步标记已读

例外一：FR-22C 版本更新 → 仅 App 内弹窗，两条都不走
例外二：FR-22E 兽医端 → 仅系统推送，不写 notifications 表（兽医端 V1 无通知中心）
```

**关键规则（`db-schema-reference.md` `notifications` 表注释，合规硬约束）：**

> 通知标题（`title`，≤120 字符）/ 正文（`body`，≤255 字符）**绝不含健康数据明文**。

这条约束直接影响文案：兽医回复推送只能写「你的宠物问诊有新回复」，**不得**带入症状、AI 评级、用药建议等任何内容。同理 `REFUND_REJECTED` 不含金额/账号等敏感信息。

## 3. 推送权限申请（FR-22D 推送部分）

> 来源：V1.0.0 PRD FR-22D、V1.1.0 PRD §3.12「FR-22D 补充」（V1.1.0 版本为准，两版一致）；页面 P-09。

**核心原则：不在 App 首次启动时请求推送权限**（授权率极低）。

**两个触发时机，满足任一即触发，全局仅请求一次：**

| 触发时机 | 弹出位置 | 权限请求文案（中文工作稿） |
| --- | --- | --- |
| 用户**完成第一次问诊**后 | 问诊结果页关闭后立即弹 | 「开启通知，兽医回复时第一时间提醒你」 |
| 用户**完成宠物档案创建**后（仅从未问诊的用户） | FR-0G 档案创建「创建成功」庆祝页之后、进入首页之前立即弹 | 「开启通知，第一时间收到 [宠物名] 的生日提醒和陪伴纪念日」 |

**后果：**

- 两个时机均已触发过（或用户已授权）时，不再重复弹起
- 用户拒绝后**不再主动弹起系统权限弹窗**
- 可在「我的」页面引导用户手动前往设置开启
- **FR-0G 流程串联：** 完成创建 → 「创建成功」庆祝页 → 推送权限弹窗 → 进入首页

**测试口径（`test-cases-zh.md` TC-22D-01~04）：**

- TC-22D-01：首次安装打开 App，**不**立即弹权限
- TC-22D-02：完成首次问诊（AI 或兽医均可）、结果页关闭 → 立即弹，文案为「兽医回复」版
- TC-22D-03：从未问诊、刚完成建档 → FR-0G 结束后立即弹，**用户确认权限后再进入首页**
- TC-22D-04：任一时机已触发过（无论授权与否），另一时机满足时**不再弹**

**⚠️ 版本边界：** V1.1.4 FR-85 会把这套逻辑改为「多触发点、每点各一次」。**本次补做按上表的「取最早者、全局一次」实现**，不要提前实现 FR-85。另注意 V1.1.4 FR-70 手机号软引导虽借用同一组时机定义，但**必须是相互独立的两套触发计数，不可共用同一个「是否已触发」标记位**。

### 4.2 问诊类通知的补充规则

**N-01 兽医回复：**
- 用户**未在当前页面查看对话时**才触发推送；用户正在查看该对话时**不重复推送**（TC-22A-01/02）
- 与「问诊」Tab 红点联动：有兽医回复未读时 Tab 显示红点（FR-19）；用户在兽医咨询对话中切到其他 Tab，会话在后台**保持连接、不中断不关闭**，红点持续显示

**N-02 问诊已完成（FR-31 评分确认门）：**
- 兽医点击「结束会话」→ 会话进入「待关闭」状态（**非立即关闭**）→ 用户侧收到本通知
- 用户在 **30 分钟保护窗口**内仍可发消息，兽医收到推送可继续回复
- 30 分钟内评分 → 会话正式关闭；未评分 → 自动关闭并记为「未评分」
- 超时未评分的补评分弹窗**不走推送**，改为用户**下次进入问诊页面**时弹出一次（FR-33）

**N-03 兽医接单（文案已按现实重写，2026-08-06）：**
- 触发点：FR-30 抢单流程第 5 步「兽医点击接单成功」的那一刻
- **V1.0.0 原文案「兽医已接受你的问诊，点击开始对话」作废**——V1.1.0 FR-43D 改为「免费入队、接单后限时支付」后，接单不再直接建会话，而是先弹 **1.5 分钟（90 秒）限时支付页**，支付成功才建会话
- 新文案与跳转见 §4.1 N-03 行及附录 A；跳转目标为**限时支付页**，不是会话
- 用户正在等待界面内时**直接跳转支付页**，不依赖推送；推送仅覆盖用户已离开等待界面（切后台/切 Tab）的情况
- **⚠️ 投递时效是这条通知的硬约束**：支付窗口只有 90 秒，推送延迟直接吃掉窗口。补做时须：
  - Android 用 `high` priority、iOS 用 `time-sensitive` interruption level，绕开系统聚合/延迟投递
  - 用户去充值 PawCoin 期间倒计时暂停（FR-50A），返回后**计时恢复而非重新计满**，推送不重发
  - 建议同时评估 App 内强提醒形态（如前台全屏拦截层），不单靠系统推送
- **⚠️ `notifications` 表 type 枚举中没有对应值**，需新增 `VET_ACCEPTED`（见 §9.2）

**N-22 兽医端新请求：**
- 触发条件：用户提交**兽医咨询**请求（**AI 问诊不触发**，TC-22E-02）
- 推送对象：当前在线状态为「在线」（FR-32）的所有兽医账号；**离线兽医不接收**（TC-22E-01）
- 兽医端 V1 无通知中心，**只走离线推送**，不写 `notifications` 表

### 4.3 内容互动类通知的补充规则

- **不做通知合并**：V1.0.0 与 V1.1.0 均明确「单条逐条推送，后续版本可考虑批量合并」（TC-22B-03）
- 用户对**自己**内容点赞不通知（FR-23）；同理自评自回不通知
- **点赞通知确认要做**（2026-08-06 产品拍板，撤销 FR-23 正文批注「先不做首页点赞」的悬置状态）
- **评论与回复须区分两条文案**：一级评论 → 通知**内容作者**（N-05a）；二级评论 → 通知**被回复的评论者**（N-05b，FR-24）。原 V1.1.0 文案汇总表只有「有人评论了你的内容」一条，用在回复场景语义不符，附录 A 已拆为两条
- **二级评论只通知被回复的评论者，不额外通知内容作者**（FR-24 原文只写了「回复触发推送通知给**被回复的评论者**」）。这一条须显式声明，否则工程容易把二级评论也算作「对内容的评论」而同时触发 N-05a —— 那样内容作者会在自己帖子下的每一次回复往来中被反复打扰
- 承上：若内容作者本人就是被回复的评论者（作者在自己内容下评论、他人回复了它），该次只发 **N-05b 一条**，不叠加 N-05a

#### 4.4.1 ⚠️ 里程碑推送的两种形态，以及与生日/纪念日的重叠（实现前必须裁定）

**问题一：FR-42 里的「推送」其实是两件不同的事，源 PRD 没有区分。**

| | (a) 节点提醒推送 | (b) 达成通知 |
| --- | --- | --- |
| 来源 | FR-42 里程碑清单里「触发方式 = **系统推送提醒 + 用户当天发布**」这一列 | FR-42 后果：「**L 级里程碑完成（无论触发方式）** → 推送至通知中心并发送系统推送」 |
| 目的 | **催用户当天去发一条 Diary**（发了才算完成该里程碑） | **告知已完成**，引导去看故事 |
| 时机 | 节点当天，**完成之前** | 完成的那一刻 |
| 驱动方式 | **每日扫描**（定时） | **事件驱动**（不需要扫描） |
| 涉及里程碑 | 仅 C-L1/D-L1/G-L1（第一个生日）、C-L2/D-L2/G-L2（满 100 天）、C-L3/D-L3/G-L3（满 365 天） | **全部** L 级（含 C-L4 复合、C-L5 记满 30 条等系统自动型） |
| 跳转 | 应跳**发布页**（预选 Diary） | Diary Tab → 里程碑列表页 |
| 文案 | **源 PRD 从未定义**，见下方缺口 | 「里程碑达成 🎉 / [宠物名] 完成了「[里程碑名]」！…」（已定义，= N-08） |

**结论：** 本文档主表里的 **N-08 只覆盖 (b) 达成通知**。**(a) 节点提醒推送在所有源 PRD 里都没有文案、没有编号、没有跳转定义**——它只作为 FR-42 清单表格里「触发方式」一栏的四个字存在。而 `scheduled_push_marks` 的 `push_kind = MILESTONE_NODE` + `node_key = FIRST_BIRTHDAY`（DB 注释原文举例）显然是给 (a) 准备的。**即：DB 为 (a) 预留了去重位，但 PRD 从没写过 (a) 长什么样。**

**问题二：(a) 与生日/纪念日推送在同一天撞车。**

| 日子 | 会触发的推送 | 条数 |
| --- | --- | --- |
| 宠物生日**前 1 天** | N-06 生日提醒 🎂 | 1 |
| 宠物**第一个生日当天** | (a) C-L1 节点提醒 → 若当天发布 → (b) N-08「完成第一个生日」 | 最多 2（且与前一天的 N-06 连着三条） |
| 陪伴满 **30 天** | N-07 陪伴纪念日 🎉（C-M8 是 M 级，不发通知） | 1 ✅ 无冲突 |
| 陪伴满 **100 天** | N-07 陪伴纪念日 🎉 **+** (a) C-L2 节点提醒 → 若当天发布 → (b) N-08「完成陪伴满 100 天」 | **最多 3** |
| 陪伴满 **365 天** | 同上 | **最多 3** |

**去重表挡不住这个重叠**：`scheduled_push_marks` 的唯一键是 `(pet_profile_id, push_kind, node_key)`，而 N-07 的 `push_kind = COMPANION_ANNIVERSARY`、(a) 的 `push_kind = MILESTONE_NODE` —— **两条属于不同 push_kind，各占一条去重记录，会真的都推出去**。

**✅ 裁定（2026-08-06，产品拍板）：(a) 节点提醒推送不单独存在，由 N-06 / N-07 吸收。**

| # | 决定 | 连带修改 |
| --- | --- | --- |
| ① | **N-07 陪伴纪念日改为「催发布」定位**：跳转由「Diary Tab」改为**统一发布入口「+」预选 Diary 类型**；正文由「快去看看 TA 的成长故事」改为「**记录一下这一天吧**」。一条推送同时完成「告知纪念日」与「催当天发布」，**C-L2/C-L3 的节点提醒不再需要独立存在** | V1.0.0 PRD **FR-41**（后果·通知内容+跳转）、**FR-38** 深链表、**FR-34** 通知中心列表；V1.1.0 PRD §3.12 **FR-41**、**FR-38** 深链表、**通知文案汇总表** |

**裁定后每个节点的推送条数：**

| 日子 | 推送 | 条数 |
| --- | --- | --- |
| 宠物生日前 1 天 | N-06 生日提醒 🎂（跳发布页） | 1 |
| 宠物生日当天 | **无**（C-L1 靠 ±1 天窗口吸收） | 0 |
| 陪伴满 30 天 | N-07 陪伴纪念日 🎉（跳发布页） | 1 |
| 陪伴满 100 / 365 天 | N-07 陪伴纪念日 🎉 → 用户当天发布则 + N-08 达成通知 | 最多 2 |
| 任意 L 级里程碑完成 | N-08 达成通知 | 1 |

**裁定后 `scheduled_push_marks.push_kind = MILESTONE_NODE` 的角色变化：** 该取值原本是为 (a) 节点提醒的每日扫描去重准备的（DB 注释举例 `node_key = FIRST_BIRTHDAY` 即属此类）。(a) 取消后，它**不再有每日扫描的消费方**，但**保留使用**——改作 (b) N-08 达成通知的**幂等保护**：里程碑完成事件可能因重试/并发被重复投递，写入 `(pet_profile_id, MILESTONE_NODE, 里程碑 ID)` 可保证同一里程碑的达成通知只发一次。`node_key` 取里程碑编号（`C-L1`/`D-L2`/`G-L3` 等），不再使用 `FIRST_BIRTHDAY` 这类语义键。**`db-schema-reference.md` 中该字段的注释需按此同步更新**（并入 §9.2 前置一的文档更新项）。

**为什么满 30 天也改跳发布页：** 满 30 天没有绑定 L 级里程碑（C-M8 是 M 级、系统自动、不发通知），本可维持跳 Diary Tab。但统一跳发布页有两个好处——①催发布本身对产品有益，陪伴满月值得记一笔，且产生内容就是留存锚点（FR-12 设计意图）；②三个节点统一跳转，实现上不必按 `node_key` 分支。

**未采纳的两个方案（留档备查）：**

- **保留 (a) 独立 + 错峰投递**：错峰只是把三条摊到一天不同时段，用户当天仍收三条；且需为一条本可不存在的推送补齐文案、印尼语审核、编号与跳转定义，成本不划算
- **C-L1/L2/L3 改为系统自动**（参照 V1.1.2 FR-86 健康类里程碑取消打卡的先例）：方向一致，但 L 级完成后要**自动生成分享卡片**（FR-42），卡片需要当天的照片撑起来；改系统自动会产出一张没有内容的空卡片，把 L 级最有价值的部分做没了。健康类里程碑无此包袱，故不宜照搬

## 6. 全局通知中心（FR-34）

**入口：Discovery（原首页）顶部导航栏右侧铃铛图标**（页面 P-13，入口来自 P-10）。

> **`[决策 2026-08-06]` 铃铛随 Feed 一起挪。** V1.1.2 FR-78 把首页 Feed 改名 Discovery 并移至第 4 位，**铃铛图标作为该页顶栏的一部分一并迁移，不单独拆出、不另设入口**。即通知中心入口 = Discovery Tab 顶栏右侧，本条同时闭合原 OQ-N1。
>
> **已知代价（需上线后观测）：** Discovery 不再是任何用户的冷启动落地页（落地为 Diary 或 Discovery，按状态分流），入口从"开屏即见"退化为"需先切到第 4 个 Tab"。**未读通知的感知渠道因此高度依赖系统推送本身**——这反过来抬高了本次补做的重要性：推送没接通时，用户几乎不会主动发现通知中心里的未读内容。建议补做时一并在 Discovery Tab 图标上加未读红点（当前仅铃铛本身有角标），让未读状态在其他 Tab 也可见。**Tab 级红点为本文档建议项，需 PM 确认是否纳入范围。**

**后果：**

- 有未读通知时显示**红色数字角标**（TC-34-01）；未读条数即 `notifications` 中 `is_read = false` 的行数
- 点击进入通知列表页，**按 `created_at` 时间倒序**展示所有通知（索引 `recipient_user_id, created_at DESC` 已建）
- 通知条目**点击后标记为已读**（TC-34-02），写入 `read_at`
- **用户通过系统推送直接跳转目标页时（未经过通知中心列表），通知中心内对应条目须同步标记为已读**（TC-34-03）——这是补做中最容易漏的一条
- 访客态（未登录）点击铃铛 → 触发 P-04 登录引导（`page-list.md`）
- 非正常态支持：PL（骨架屏）· L（加载）· E（空状态）

**列表分页与保留期（PRD 未定义，本文档补充）：**

FR-34 只写了「按时间倒序展示**所有**通知」，没定义分页规则，也没定义 `notifications` 的保留期——按现有口径这张表会无限增长，通知中心也会无限长。补做时须一并明确：

- **分页**：建议首屏 20 条 + 触底加载 20 条（与 FR-17 Feed 的 20 条口径一致），不做「全部一次性拉取」
- **保留期**：建议服务端只保留最近 **90 天**的通知，超期物理删除（定时任务）。理由：通知是提醒载体而非业务记录，真实业务数据（问诊、订单、工单）各有自己的历史页；无限保留只会拖慢查询并增加 PDP 合规面
- **账号注销联动（合规必做）**：`notifications` 含 `recipient_user_id`，属个人数据。V1.0.0 FR-20 账号注销时**须将该用户的全部通知记录一并物理删除**（与 V1.1.0 FR-45B「账号整体注销会将健康记录随账号数据全部删除，印尼 PDP 合规强制」同一口径）。注销后的通知不适用匿名化保留（不同于 UGC 内容）
- **上述三项均为本文档建议值，需 PM 确认**（见 §9.3 OQ-N8）

## 7. 数据模型

### 7.1 `notifications`（已建）

> 用户通知记录表：所有发给用户的站内通知/推送每发一条写一行，是 App「通知中心」列表的读取来源。**发给兽医的推送不写本表**（兽医端 V1 无通知中心，只走离线推送）。**通知标题/正文绝不含健康数据明文。**

| # | 字段 | 类型 | 说明 |
| --: | --- | --- | --- |
| 1 | `id` | bigint PK | 通知 ID |
| 2 | `recipient_user_id` | bigint | 收件人（关联 `users.id`） |
| 3 | `type` | varchar(32) | 通知类型枚举，见下 |
| 4 | `title` | varchar(120) | 标题（通知中心 + 推送横幅），**无健康数据明文** |
| 5 | `body` | varchar(255) | 正文摘要，**无健康数据明文** |
| 6 | `deep_link_type` | varchar(32) | 跳转目标页面类型，通常同 `type`，可为空=无跳转 |
| 7 | `deep_link_token` | varchar(64) | 对外随机不可猜测串，**仅用于标记已读** |
| 8 | `target_ref` | varchar(64) | 跳转目标资源内部标识，**客户端跳转依据此字段** |
| 9 | `is_read` | boolean | 未读体现为首页红点角标，默认 false |
| 10 | `created_at` | timestamptz | UTC，通知中心按此倒序 |
| 11 | `read_at` | timestamptz | 标记已读时间，未读为空 |

**索引：** `recipient_user_id, created_at DESC`

**现有 `type` 枚举（16 个）：**

`VET_REPLY` · `CONSULT_CLOSED` · `CONTENT_LIKED` · `CONTENT_COMMENTED` · `NEW_CONSULT_REQUEST` · `PET_BIRTHDAY` · `COMPANION_ANNIVERSARY` · `MILESTONE_NODE` · `CONTENT_REMOVED` · `REPORT_REVIEWED` · `CONTENT_REVIEW_APPROVED` · `CONTENT_REVIEW_REJECTED` · `REFUND_REJECTED` · `TICKET_RESOLVED` · `CSAT_SURVEY` · `IDENTITY_REQUIRE_MODIFY`

其中 `TICKET_RESOLVED` / `CSAT_SURVEY` / `IDENTITY_REQUIRE_MODIFY` **为预留类型，尚未实际发出**。

### 7.2 `scheduled_push_marks`（已建）

> 定时推送去重标记表：记录「某个宠物档案的某个节点已经推过了」，防止生日/纪念日/里程碑这类每日扫描的定时推送重复打扰用户。**每天扫描后逐条投递前先查此表**，`(宠物档案, 推送种类, 节点标识)` 三者唯一，是「同一节点只推一次」的**唯一判定依据**。

| # | 字段 | 说明 |
| --: | --- | --- |
| 1 | `id` | PK |
| 2 | `pet_profile_id` | 关联宠物档案 |
| 3 | `push_kind` | `PET_BIRTHDAY` / `COMPANION_ANNIVERSARY` / `MILESTONE_NODE` |
| 4 | `node_key` | 生日=年份；纪念日=天数节点；里程碑=节点 ID |
| 5 | `pushed_at` | 投递时间（UTC） |

**索引：** 🔑唯一 `pet_profile_id, push_kind, node_key`

### 7.3 `users.locale`（已建）

> 用户语言偏好，**用于系统推送按用户语言渲染文案**。取值 `id`（印尼语）/ `en`（英语），由 App 请求头 `Accept-Language` 捕获；**为空视为默认 `id`**。

推送投递服务必须读取此字段选择文案语言，不得只发单语言。与 FR-27 语言设置一致：设备为印尼语→印尼语；英语→英语；其他→默认英语（**注意：FR-27 的兜底是英语，`users.locale` 的兜底是印尼语，口径不一致，见 §9.1 冲突 C-5**）。

**成本说明（重要）：** `notifications.type` 的物理类型是 **`character varying(32)`，不是 PostgreSQL enum**。因此「扩枚举」**不需要 DB migration**，也不存在锁表风险——它是一个应用层约定的取值集合。实际工作量为：

1. **后端**：常量表新增 5 个取值 + 5 个通知构造函数（填 `type` / `title` / `body` / `deep_link_type` / `target_ref`）

3. **文档**：更新 `db-schema-reference.md` 中 `notifications.type` 字段的枚举说明（该注释是唯一的取值权威，不更新会持续误导下游）；**同批更新 `scheduled_push_marks.node_key` 的注释** —— C-6 裁定后 `MILESTONE_NODE` 改作 N-08 达成通知的幂等保护，`node_key` 取里程碑编号（`C-L1`/`D-L2` 等），不再是 `FIRST_BIRTHDAY` 这类语义键（见 §4.4.1）
4. **同批标注废弃**：`CONTENT_REVIEW_APPROVED`、`IDENTITY_REQUIRE_MODIFY` 两个取值因 C-1/C-2 裁定不再使用，注释中标为「保留不使用」而非删除（历史数据可能已有该值）

> **N-20 独立枚举的理由（已确认不复用 `CONTENT_REMOVED`）：** 两者收件人不同（内容作者 vs 评论作者）、文案不同（Kontenmu vs Komentarmu）、跳转不同。复用会导致通知中心里两类条目无法区分渲染。

#### 前置一：给 `notifications.type` 加 5 个取值

**背景：** `notifications` 表的 `type` 字段是一个**取值集合**——每条通知写进去时要标明自己是哪一类，客户端再根据这个值决定「通知中心里这条长什么样、点了跳哪」。这个集合当前有 16 个值，是在 V1.0.0/V1.1.0 建表时定下的。

**问题：** 我们这次归集出的 22 条通知里，有 5 条**在这个集合里找不到自己的位置**：

| 通知 | 需求早就写了 | 但 type 集合里没有 |
| --- | --- | --- |
| 兽医接单（N-03） | V1.0.0 FR-30 抢单流程第 5 步 | ❌ |
| 昵称被重置（N-17） | 审核方案 §8.1，**印尼语文案都定稿了** | ❌ |
| 宠物名被重置（N-18） | 审核方案 §8.2，**印尼语文案都定稿了** | ❌ |
| 头像被重置（N-19） | 审核方案 §8.10，**印尼语文案都定稿了** | ❌ |
| 评论被下架（N-20） | 审核方案 §8.5，**印尼语文案都定稿了** | ❌ |

不补的后果：这 5 条通知**写不进 `notifications` 表**，也就发不出去。审核方案 §8 那批定稿的印尼语文案会一直躺着没人用。

**好消息是成本很低。** 我核对过 schema：`type` 的物理类型是 `character varying(32)`，**是普通字符串字段，不是 PostgreSQL 的 enum 类型**。这个区别很关键——如果是 enum，加值要跑 DB migration、有锁表风险；是 varchar 的话，「加值」纯粹是应用层约定，**动数据库一行都不用改**。

**具体要做的四件事：**

- [ ] **后端**：常量表加 5 个字符串取值，配 5 个通知构造函数（负责填 `type` / `title` / `body` / `deep_link_type` / `target_ref` 五个字段）
- [ ] **客户端**：`deep_link_type` → 页面路由的映射表加 5 条 —— `VET_ACCEPTED` 跳限时支付页；`NICKNAME_RESET` 跳「我的」昵称编辑；`PET_NAME_RESET` 跳宠物档案编辑页；`AVATAR_RESET` 跳对应头像上传入口；`COMMENT_REMOVED` 无跳转
- [ ] **文档**：更新 `db-schema-reference.md` 里 `notifications.type` 那一行的字段说明 —— **这条注释是全项目唯一记录了取值集合的地方**，不更新的话，下一个来读 schema 的人还是会以为只有 16 个值
- [ ] **顺手标废弃**：`CONTENT_REVIEW_APPROVED` 和 `IDENTITY_REQUIRE_MODIFY` 这两个值因为下面「前置二」的原因不再使用了，在注释里标成「保留不使用」。**不要删** —— 历史数据里可能已经写过这两个值，删了会导致老通知渲染不出来

#### 前置二：改掉两份后台 PRD 里已经过时的通知描述

**背景：** 2026-07-08 那次审核方案改版，推翻了两个原本的处置模型。但**只改了审核方案自己，两份后台 PRD 还停留在旧模型**。后台是运营真正操作的地方——后台 PRD 怎么写，后台工程就怎么做，运营就怎么点。现在的状态是：审核方案说 A，后台 PRD 说 B。

**问题一：`V1.0.0/v1.0.0manager_prd.md` 的 AB-3C**

AB-3C 是「帖子高风险人工审核队列」。它现在这么写运营审完之后会发生什么：

> - **通过**：内容立即正常发布，进入 Feed 和「我的发布」，**用户收到通知「你的内容已通过审核，现已发布」**
> - **拒绝**：内容丢弃，用户收到通知「你发布的内容因违反社区规定，未通过审核」，不说明具体原因
> - **超过 3 天未处理自动丢弃**：……用户收到通知「你发布的内容违反社区规定，请重新发布」

但审核方案 §8 定了条总原则：**只有负向结果（隐藏/违规/未通过）才推通知，正向结果一律静默**。§8.6 专门说了这条：

> 原设计（V1.0.0 AB-3C）会推送「你的内容已通过审核，现已发布」，现依「隐藏才通知」原则**取消该正向通知** —— 帖子静默转为正式展示即可（作者本就能在「我的发布」看到该帖）。

- [ ] **改法**：把 AB-3C「通过」那一条里的通知句删掉，改成「内容立即正常发布，进入 Feed 和「我的发布」，**静默转正，不通知用户**」，加个脚注指向审核方案 §8.6。
- [ ] **注意别改多**：「拒绝」和「超时丢弃」这两条通知**保留不动** —— 它们是负向结果，按总原则本来就该发，对应我们文档里的 N-12 / N-13。

**问题二：`V1.1.0/v1-1-0后台prd.md` 的 AB-9B 和 AB-9C**

这两节讲的是「昵称/宠物名被判定违规之后怎么处置」。它们描述的是一套**「限期整改」模型**：

AB-9B 的处置动作表里有这么一行：

> | **要求修改** | 向用户发送系统通知「你的[昵称/宠物名]包含不当内容，**请在 7 天内修改，否则账号功能将受限**」；字段在其他用户界面替换为「\*\*\*」展示（本人可见原内容），直到用户修改并通过审核 |

AB-9C 接着描述后续链路：

> - 新内容通过 → 「\*\*\*」屏蔽自动解除，内容恢复正常展示；**通知用户「你的[昵称/宠物名]已审核通过」**
> - **逾期未修改处理**：超过 7 天用户仍未提交修改 → 系统自动限制该账号功能（不可发帖、不可评论，可正常浏览），**并再次推送提示通知**

而审核方案 §3.3 在 2026-07-08 把整套模型换掉了：

> **处置模型说明（2026-07-08 决策）：** 取消原「要求修改 + 7 天期限 + 逾期限权 + 星号遮蔽显示」机制，改为**判定违规即重置为默认编码名** —— **无宽限期、无账号功能限制、无屏蔽占位**。默认编码名由后端生成（如昵称 `user_8f3a2b`、宠物名 `Pet_8f3a2b`），用户重设新名即重新走审核。

**新旧模型的差别，一句话：** 旧的是「警告你去改，不改就封功能」；新的是「直接给你换成系统默认名，不罚你，你想改随时改」。

这直接影响三条通知：

| 旧模型的通知 | 新模型下 |
| --- | --- |
| 「请在 7 天内修改，否则账号功能将受限」 | **删掉** —— 没有 7 天期限了，也不限权了。取而代之的是审核方案 §8.1/§8.2 的「你的昵称/宠物名已被重置」（= 我们文档的 N-17/N-18） |
| 「你的[昵称/宠物名]已审核通过」 | **删掉** —— 正向结果不推送（§8.4 已明确删除该通知） |
| 逾期未修改的「再次推送提示通知」 | **删掉** —— 逾期机制整个不存在了 |

- [ ] **AB-9B 改法**：处置动作表里「要求修改」整行作废（连带那套 `***` 遮蔽展示逻辑），替换为「**违规** → 系统将该字段重置为默认编码名（`user_xxxxxx` / `Pet_xxxxxx`），并推送审核方案 §8.1/§8.2 通知」。「不违规（放行）」那一行保留不变（本来就不通知）。
- [ ] **AB-9C 改法**：整节重写或删除。新模型下不存在「限期内提交新名 → 重新审核 → 通过后解除屏蔽并通知」这条链路了。用户重设新名后就走常规异步审核，通过则静默生效，没有任何通知。
- [ ] **收尾**：这两处改完，前置一里说的 `CONTENT_REVIEW_APPROVED`（对应问题一）和 `IDENTITY_REQUIRE_MODIFY`（对应问题二）才能正式标为「保留不使用」—— 因为到那时才真的没人会再发这两类通知了。

> **归属提醒：** 这两份是**其他版本**的 PRD（V1.0.0 和 V1.1.0），改动需对应文档 owner 点头，本文档不代改。
