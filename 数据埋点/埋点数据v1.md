## 0. 0716 最新盘点带来的几个更新（覆盖/修正此前判断）

1. **全局 `button_tapped` autocapture 是新发现的兜底数据源**——挂在根节点，拦截所有可点击控件的点击，带 `button_name`（脱敏后的按钮文案）。这意味着很多"有没有埋点"的问题可以退而求其次靠它反推，但**粒度很粗**（拿不到业务属性如 post_id、无法区分同一按钮的不同实例），不能替代下面列的专门业务事件，只作为过渡期兜底。
2. **新发现 P0 级问题：环境未隔离**——staging 包和生产包默认共用同一个 PostHog project token，测试数据和真实用户数据混在一起，**污染本清单几乎所有指标的准确性**，建议优先级不低于任何具体业务埋点，因为不修的话，后面新加的埋点算出来的数字也是脏的。
3. **成功/失败态缺失的范围比此前认知的更大**——不只是登录，现有 9 个手工事件全部只有"点了/提交了"，没有对应的"成功了/失败了"。比如 `triage_submitted` 没有 `triage_succeeded`/`triage_failed`，`pet_profile_create_submitted` 没有 `pet_profile_created`。之前只提了 `login_succeeded` 一条，这次按同样逻辑把其余几个一并列出。
4. **Tab 切换 `$screen` 缺口需要重新确认**——0716 这份盘点没有复现或提及这个问题，但 `deferred-work.md` 有明确到 commit 级别的记录（`StatefulShellRoute.indexedStack` + `goBranch` 绕过 `PosthogObserver`）。两份材料对不上，**建议工程直接实测一次**（比如切换 Tab 后看 PostHog 后台是否有对应 `$screen` 事件），而不是默认相信任何一份文档。
5. **V1.1.0 相关页面的状态存疑，需要重新核实**——0716 盘点点名提到"PawCoin 充值、GemPay 支付、退款、客服工单、身份证（KTP）、健康记录、新手任务（Lulus Pemula）"这些是"V1.1 新功能零埋点"，措辞暗示这些**页面本身可能已经存在**（哪怕走 mock/占位后端），这和我们 7/15 核查代码"V1.1.0 完全没有开始写代码"的结论不一致。**这个出入直接决定市场部要的「Pet ID Cards created」这个指标现在能不能算**（见 §2），建议先确认这批页面到底是真实现还是走 mock，再决定是否现在就能挂埋点。
6. **新发现：兽医端（`/vet/*`）全流程零埋点**——工作台、接单、回复全都没有业务事件，此前的分析没有专门覆盖这块。
7. **新发现：无埋点单测**——`sanitizeTapLabel`/`scrub`/`distinctIdFor` 三个纯函数标注了"L0 可测"但实际没测，工程债，优先级低，顺带一提。

## 1. 内容运营《Knowledge 细分类目指标需求》分析

### 1.1 需求内容与合理性判断

运营希望在 Knowledge（知识类）大类下新增 3 个子类（① 宠物饲养介绍 ② 新手养宠指南 ③ 常见病例内容），用于更细颗粒度地判断内容效果、决定资源分配。**判断：这个诉求本身合理且有价值**——"哪类知识内容值得多投入"是内容团队应该有数据支撑的决策，Growth/Daily 两个大类不涉及改动，改动范围可控。

| 指标 | 算法 | 合理性判断 |
|---|---|---|
| 子类渗透率 | `(点赞用户+评论用户去重) / 活跃用户` | 合理，但"活跃用户"口径依赖 §0.4 的 Tab 埋点问题，需先解决口径问题 |
| 子类活跃比 | `子类目(点赞+评论) / 大类目(点赞+评论)` | 合理，纯用现有 `content_likes`/`comments` 数据即可，**不需要新埋点，只需要子类标签** |
| 子类点击率 | `子类内容点击次数 / 子类内容Feed曝光次数` | 合理，但分母"Feed 曝光"目前完全没有埋点，运营自己也在文档里点明了这一点 |
| 子类目分享率（1.2.0 起） | `分享次数 / 点击浏览次数` | 依赖"单条内容分享"功能本身，**该功能在 V1.0.0/V1.1.0/V1.2.0 三版 PRD 里都没有规划**（V1.0.0 §5 明确"不做单条内容的外部分享"；V1.2.0 唯一的"收藏/分享"相关功能是"收藏兽医"FR-67 和"宠物年龄换算分享卡"FR-65，都不是这里说的"内容分享"）——运营自己已经标注这是未来需求，判断正确，但连"1.2.0 就能上"这个假设都需要产品重新确认，不要默认成立 |
| 分享转化率（1.2.0 起） | `分享带来的新增注册数 / 分享次数` | 需要分享链接的归因链路（深链接/邀请码），和《数据v1.0.0-v1.1.0》里 SM-2 宠物名片分享的归因需求是**同一类基础设施**，建议合并成一套，不要分别建两套 |

**关于"收藏"**：文档在 Open Questions 里提到希望子类标签能和"点赞/评论/收藏/曝光/点击/分享"数据关联导出。**收藏(Save)这个交互类型目前不存在**——V1.0.0 PRD 明确"不做收藏"，V1.1.0/V1.2.0 全文检索"收藏"也只有"收藏兽医"（FR-67，完全是另一个功能，收藏对象是兽医账号不是内容）。这一条应该从"需要关联的数据"里去掉，等未来真的规划了内容收藏功能再补。

**关于统计口径规范**（总量法而非逐条平均、发布后 N 天观察窗口、报表节奏日/周更新）：这些是数据计算规范，不是"埋点"需求，不需要新增采集，但需要在数据字典/BI 层面按这个口径实现，这里记录下来避免后续被遗漏。

### 1.2 隐含的埋点/数据基建需求（已合并进 §3 总表，此处只做索引）

- Knowledge 内容子类标签字段（新增，见 §3 P0）

## 2. Monthly Marketing Scorecard 分析

**核心判断：这份文档里大多数指标不该由产品埋点覆盖，是市场团队自己的渠道数据，不建议工程为它们单独开发埋点。**

| 指标 | 数据从哪来 | 是否需要产品埋点 |
|---|---|---|
| Marketing spend、Blended/Paid CPI | 广告平台（Meta/TikTok/Google Ads）后台自带 | 否——纯广告平台数据 |
| Social impressions（TikTok+IG）、Social followers、Avg. share rate | 社媒平台自带创作者/企业号后台 | 否 |
| Creator external posts、Active creators | 达人管理表格，市场团队自行维护 | 否 |
| Merchant/partner locations live | 商务拓展记录，人工登记 | 否 |
| Media articles | PR 团队人工登记 | 否 |
| App store rating | App Store Connect / Google Play Console 自带 | 否 |
| **Total new installs（含 organic/paid 拆分）、Blended/Paid CPI 的准确性** | 需要区分"自然量"和"付费量"，PostHog 本身不做广告归因 | **✅ 需要——这是本次三份文档里唯一「不建就整个板块都算不出来」级别的基础设施缺口**：需要接入 MMP（Mobile Measurement Partner，如 AppsFlyer/Adjust），目前全仓检索不到任何 MMP SDK 的痕迹，见 §3 P0 |
| D1/D7 retention、DAU（月末） | 依赖"活跃用户"口径 | 依赖 §0.4 Tab 埋点问题，不是新增埋点而是修复已知缺口，见 §3 P0/P1 |
| **Pet ID Cards created（累计）** | 依赖 V1.1.0 身份证功能（FR-49）| ⚠️ **状态存疑**，见 §0.5——需要先确认该功能是否已有前端实现，再决定埋点方案，见 §3 P2 |

**结论**：市场团队应该继续用广告平台/社媒平台/App Store 后台的原生数据填这张表的大部分行；产品工程真正需要投入的只有「安装归因 SDK」「活跃口径修复」「Pet ID Cards 埋点（待功能状态确认）」这三项，其余不建议排期。

## 4. 明确不属于本清单（不需要工程排期）

1. **市场 Scorecard 里的外部渠道数据**——广告花费/CPI 原始数、社交曝光/粉丝数、达人数据、商户网点、媒体报道、App Store 评分，全部靠对应外部平台/人工登记，见 §2。
2. **人工登记类数据**——运营精选记录表、群成员数/活跃/退群、私信授权记录，详见《TailTopia-内容运营数据指标与考核方案》，运营团队自行用轻量表格记录，不进本清单。
3. **统计口径规范**（总量法、发布后 N 天观察窗、报表更新节奏）——是数据计算规则，不是采集需求，落地时体现在 BI/报表层，不需要新增埋点。
