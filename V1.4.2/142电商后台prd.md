## 1. AB-24：优惠券管理

**背景：** App 端 FR-130 引入优惠券（满减、免运），券的一切参数由运营在后台配置，App 端不写死任何一张券。现有后台无任何优惠券能力。

### 已确认项（2026-09-30 拍板）

**可配置的维度：**

| 维度 | 取值 |
|---|---|
| 券类型 | 满减 / 免运（本次只有这两种） |
| 面额与门槛 | 满减：减免金额 + 门槛金额；免运：可设门槛金额 + **最高减免金额**（2026-11-03 新增：免运券减免额取「本单最低快递运费」与此上限中较小者，见 App 端 FR-172） |
| 有效期 | 固定起止日期，或领取后 N 天内有效 |
| 数量 | 发放总量、每人限领张数 |
| 适用范围 | 全场 / 指定品类 / 指定商品 |
| 发放方式 | 新人自动发放 / 用户领取 / 兑换码。新人的定义与发放时机由 App 端 FR-130 固定，后台不可配：注册 1 个月内且从未在电商下过已支付订单的已注册用户，首次进入 Toko 时发放；有进行中的新人券时，游客进入 Toko 弹窗引导注册（2026-11-05 同步） |

- 没有系统默认券——三种发放方式都要运营建券后才存在
- 规则口径以 App 端 FR-130 为准：每单最多 1 张满减券 + 1 张免运券；满额免运与免运券并存，同时满足时系统取减得多的一个（2026-11-04）；免运券设了适用范围时须本单全部商品在范围内才可用（2026-11-04）；满减券门槛按券前商品金额判断，满额免运与免运券门槛按商品实付金额（商品金额 − 满减券）判断

### 页面位置与流程（2026-10-06 拍板）

- **位置**：🛍 商城组新增侧栏项「优惠券」，独立列表页
- **列表**：券名称、类型、面额 / 门槛、发放方式、有效期、已发 / 总量、已使用数、状态（未开始 / 进行中 / 已结束 / 已停用）；可按状态、类型、发放方式筛选
- **新建 / 编辑**：列表页右上「新建优惠券」→ 右侧抽屉表单 → 提交后回到列表并定位到新行。**已开始发放的券只能改总量（只增不减）与停用**，面额、门槛、适用范围不可改，避免用户手里同一张券前后规则不一致
- **兑换码**：发放方式选兑换码时，由运营填写一个通用码或批量生成一次性码（批量码可导出）
- **停用**：行内操作，二次确认；停用后不能再领取或兑换，**用户已领取未使用的券是否继续可用**须在确认弹层中让运营二选一
- **数据**：券详情抽屉显示领取数、占用中数（被待付款订单占用）、使用数、带来的订单金额

### 防误配提醒（2026-10-06 拍板）

面额 ≥ 门槛的满减券（等于白送商品）、总量不限且每人不限领的券，保存时给出醒目提示并要求二次确认。

### 按用户查券（2026-11-04 拍板）

用户投诉券没退回、券用不了时，客服须能按用户查到他持有的券。

- **位置**：后台现有的用户详情页新增「优惠券」标签页（线上用户详情页的结构由研发评估后确定具体放法）
- **内容**：该用户的每一张券——券名、类型（满减 / 免运）、面额与门槛、获得方式（新人 / 领取 / 兑换码 / banner）、领取时间、有效期、当前状态（可用 / 被待付款订单占用 / 已使用 / 已过期）；占用或已使用的显示对应订单号并可点进订单
- **状态变化记录**：每张券的占用、退回、使用时间，便于查「券为什么没退回」
- **只读**：客服不能修改券的状态
- **兑换码锁定**：用户因输错兑换码被锁定时（App 端 FR-130），标签页显示「兑换已锁定，X 分钟后解除」；客服不能手动解锁
- **不在本版**：客服给指定用户手动补发券（如投诉补偿）留到下一版，需配套权限与审批

## 5. AB-28：异常订单取消退款与退款打款

**背景：** App 端 FR-134 ③ 拍板：异常订单取消必须退还现金部分。现状「异常订单」页的整单取消只退 PawCoin 部分、现金部分只写审计不退款；部分取消完全不退款。

**位置：** 🛍 商城 → 「异常订单」页，现有「整单取消」「部分取消」两个处置动作（另有「联系后继续发货」，不涉及退款）。2026-11-03 按线上 1.4.1 复核：整单取消只把 PawCoin 部分退回钱包，现金部分只写进审计、不生成退款单；部分取消只回补库存、不退任何款；成长值扣回只在 PawCoin 部分实际退回时触发。

### 已确认项（2026-09-30 拍板）

- 整单取消：PawCoin 与现金部分全额退回
- 部分取消：退回被取消行对应的金额
- 现金部分的去向沿用现有退货流程：退为 PawCoin 或财务线下打款（2026-10-02 拍板）
- 平台原因的退款（缺货、运单失败、快递原因物流异常）选退为 PawCoin 时，沿用现有「转 PawCoin 补偿」配置额外补偿；用户原因被退回的取消不给（2026-11-04，见 App 端 FR-134）
- **与现状的关系：完全取代现行「整单取消不退现金、部分取消不退款」的处置结果**，两个处置入口本身保留

### 流程（2026-10-06 拍板）

- 处置确认弹层列出本次退款金额明细：PawCoin 部分、现金部分
- 提交后 **PawCoin 部分立即退回**用户账户；**现金部分**待用户在 App 订单详情页选定退款去向后处理——选 PawCoin 即时到账，选线下打款则转财务打款（App 端 FR-134）

### 退款打款（2026-11-04 拍板）

**现状（2026-11-04 核 1.4.1）：** 电商退货选「退到银行」时，系统执行退款即把订单标为已退款，处理面板只显示用户收款账户与「需人工打款」；财务在系统外转账后，系统里没有回填「已打款」的地方，查不到这笔钱打了没有。

- **位置**：🛍 商城 新增侧栏项「退款打款」，汇集所有选了**线下打款**的电商退款，来源包括：异常订单取消（本节）、取消后到账的退款（本节下文）、物流异常的用户原因取消与丢件破损赔付（AB-38）
- **权限**：只有具备现有「打款」权限（`refund.payout`）的财务可以操作
- **列表**：订单号、用户、退款金额、来源、收款渠道与账号、户名、用户提交时间、状态（待用户选择 / 待打款 / 已打款）
- **标记已打款**：财务在系统外转账后，点「标记已打款」，填写转账流水号，可上传转账截图；之后 App 订单详情由「退款处理中」变为「已退款」
- 不接入 Iris 等自动出款接口，1.4.2 保持人工转账

### 成长值扣回（2026-11-04 拍板）

- **全部自动扣回，不设人工入口**：PawCoin 部分退回、现金部分选「退为 PawCoin」时，退回即扣；现金部分选「线下打款」时，在财务点「**标记已打款**」时扣
- 扣回规则沿用 1.4.0 FR-143：按退款金额占比扣回、四舍五入，同一订单累计扣回不超过当初入账的成长值；等级可随之下降，**不通知用户**
- 扣回写入成长值流水，订单详情可看到本单已扣回的成长值

### 取消后到账（2026-11-04 拍板，承接 App 端 FR-134 ②）

**场景：** 订单 60 分钟未付款被自动取消后，用户的付款才到账。现状这笔到账通知被直接丢弃，后台查不到。

- **系统记录**：到账通知不再丢弃，记到这张已取消的订单上，标「取消后到账」并记录到账金额
- **提醒客服**：订单列表可按「取消后到账」筛选；订单详情显示标记与到账金额；每出现一笔，用后台现有的提醒方式通知客服
- **处理顺序**：
  1. **客服先联系用户**，询问是否同意由平台帮他重新下单，并核对条件是否满足（见下方核对清单）
  2. **用户同意且条件满足 → 重新下单**：订单详情点「重新下单」，系统按原订单为用户生成一张新订单，与原订单互相关联；已到账的钱用于支付 QRIS 部分，原订单用过的券与 PawCoin **正常扣除**，新订单进入待发货、正常履约
  3. **用户不同意、条件不满足或没有库存 → 退款**：点「退还到账款」，App 订单详情出现「选择退款方式」，用户选退为 PawCoin 或线下打款；**不给转 PawCoin 补偿**
- **核对清单**：点「重新下单」前，后台向客服列出须核对的事项，逐项满足才可提交：
  - 用户已同意重新下单
  - 原订单用过的券仍在用户账户中、没有被用掉；**券已被用掉则不能重新下单**，走退款。券**已过期仍可用于这张新订单**（原订单下单时券有效，按 FR-130「按下单时刻判断」的口径）
  - 用户 PawCoin 余额足以支付原订单的 PawCoin 部分（超时取消时这部分已退回用户）
  - 商品有库存
  - 收货地址仍有效
- 不提供「恢复原订单」

### 取消后到账：重新下单细节（2026-11-04 拍板）

- 新订单沿用原订单的商品、数量、收货地址、快递、保价与金额明细，**金额按原订单锁定**，不随现价、现在的运费报价变化；差额由平台承担
- 原订单所选快递现在不可用时，改选当前最便宜的一家，运费差额由平台承担
- 只有部分商品缺货：先重新下单，缺货的行再走「异常订单」部分取消（本节上文）
- 新订单沿用原订单的归属门店（商家平台返佣）
- 新订单的成长值按正常付款入账；原订单不产生成长值

## 7. AB-38：物流接入 Biteship（发货地址、包裹数据、运单）

**背景：** App 端 FR-172（2026-11-03）接入物流聚合商 Biteship：结算时按包裹重量与体积向 Biteship 询价，用户在多家快递中自选、自付运费；付款后通过 Biteship 下运单，物流轨迹由 Biteship 回传。

**现状（2026-11-03 核线上 1.4.1）：** 🛍 商城 →「服务范围与运费」页维护开通区域（Kecamatan）与每个区域的固定运费，另有满额免运门槛（0 表示不做免运）；只有 Reguler 一档，没有发货地址的概念。「订单履约」抽屉中运营手工选承运商、录运单号与承运成本，手工标记送达。商品 SKU 没有包裹重量与体积字段（只有粮量预估用的净含量，可空）。

### 已确认项（2026-11-03 拍板）

- **开通区域保留**，只决定卖不卖：收货地址须在开通区域内、且 Biteship 至少有一家快递可达才能下单。区域上的**固定运费停用**，运费改由 Biteship 报价（历史订单的运费照旧可查）
- **满额免运保留并封顶**：门槛之外新增「满额免运最高减免」，减免额取「本单最低快递运费」与此上限中较小者；**门槛 > 0 时最高减免必填，不可留空**（2026-11-04）
- **免运券新增「最高减免金额」**（见 AB-24）
- **SKU 包裹重量与长宽高必填**，没填的 SKU 在 App 端不能卖；存量在售 SKU 须在上线前补齐
- **运单通过 Biteship 下单**，不再手工录运单号
- **发货地址只有一个**：「服务范围与运费」页新增「发货地址」配置，作为 Biteship 询价与下运单的起点
- **送达**：Biteship 回传签收后订单自动标记已送达；手工「标记送达」保留作为兜底
- **运单失败**：「Biteship 下单」失败时，订单标记为「运单失败」并显示 Biteship 返回的原因，返回给运营处理。运营三选一：① **重新下单**——用同一家快递再提交一次，适用于超时、接口报错、无可约取件时段、账户余额不足等临时问题；② 联系用户后取消订单——走「异常订单」页整单取消（AB-28），PawCoin 与现金全额退回、券退回；③ 手工填写运单（快递与运单号）后继续发货。**重新下单须有报警**：短时间内重新下单次数快速上升时通知技术排查（2026-11-04）
- **保价**：用户在 App 端勾选保价时（FR-172），「Biteship 下单」一并带上保价（2026-11-04）

### 页面位置与流程（2026-11-04 拍板）

- **发货地址**：放在「服务范围与运费」页的独立卡片；未配置时 App 端无法询价，页面顶部醒目提示
- **满额免运最高减免**：放在「服务范围与运费」页满额免运门槛同一张卡；门槛 > 0 时必填，留空不能保存
- **区域列表**：固定运费列移除，只保留开通 / 停用
- **商品编辑页**：SKU 表格新增重量（g）、长、宽、高（cm）四列，保存时必填；「商品管理」列表新增「缺重量体积」筛选与标记，便于上线前补齐
- **订单履约抽屉**：「发货」改为「Biteship 下单」——显示用户所选快递与运费，确认后创建运单并预约上门取件，自动回填快递、运单号与 Biteship 实际运费（取代手工录入的承运成本）；订单履约列表可按「运单失败」筛选
- **物流异常**：订单履约列表对被退回、丢件等异常的订单加标记（处理规则见下方「物流异常处理」）
- **对账页**：每单显示用户支付的运费与 Biteship 实际运费；汇总区块见下方「对账页：优惠与物流成本」
- 订单履约抽屉与对账页显示该单是否保价及保价费

### 对账页：优惠与物流成本（2026-11-04 拍板）

**现状（2026-11-04 核 1.4.1）：** 🛍 商城 →「对账」页现有订单、PawCoin / 现金、运费、退款、赠送币几个区块，没有优惠券、保价、补偿与物流成本。

在对账页新增「优惠与物流成本」区块，时间维度沿用现有对账页：

| 项目 | 说明 |
|---|---|
| 满减券抵扣 | 平台承担的商品折扣（AB-24） |
| 满额免运减免 / 免运券减免 | 分开列，平台承担的运费 |
| 保价费收入 | 用户支付的保价费 |
| Biteship 实际运费 | 下运单时 Biteship 返回的实际运费 |
| 运费差额 | 用户支付的运费 − Biteship 实际运费 |
| 转 PawCoin 补偿 | 平台原因退款时额外发放的补偿（AB-28） |
| 待索赔 / 已索赔到账 | 物流异常的索赔（本节「物流异常处理」） |
| 退款打款 | 待打款金额、已打款金额（AB-28「退款打款」） |

### 物流异常处理（2026-11-04 拍板，承接 App 端 FR-172「物流异常」）

- **退回**：Biteship 回传退回时订单自动标「退回」。运营判定原因：
  - 快递原因：平台承担运费，免费重新发货；订单同时标「**待索赔**」，提醒运营向快递 / Biteship 处理责任认定与索赔
  - 用户原因（地址错、联系不上、拒收）：**原订单取消**，不退已花掉的运费；商品退回仓库，运营确认入库后退还商品款。用户仍想要的重新下单，按新订单发货
- **物流停滞**：物流状态 **3 天**没有更新时自动标「物流停滞」，提醒运营去 Biteship 追件
- **丢件、破损**：运营确认后手工标记。用户买了保价按商品价值赔付；没买由客服与用户协商。订单同时标「待索赔」
- 订单被标为退回、丢件或破损后，App 端订单详情显示「配送异常，请联系平台客服」

### 物流异常处理细节（2026-11-04 拍板）

- 订单履约列表新增筛选：退回 / 物流停滞 / 丢件破损 / 待索赔
- 「待索赔」标记由运营在索赔结束后手工清除，清除时填写索赔结果与到账金额，进入对账页
- 「重新发货」只用于快递原因：在原订单上再走一次「Biteship 下单」，运费记为平台成本
- 用户原因取消须在退回商品**确认入库**后才能提交退款；入库沿用现有「退货与拒收的货」入库入口
- 用户原因取消与丢件破损赔付的退款，复用「异常订单」页的整单取消（AB-28），新增「扣除运费与保价费」选项（扣的是用户实际支付的运费，即运费减去满额免运或免运券后的部分）；**现状「异常订单」页只处理发货前的订单**，须放开到已发货且带物流异常标记的订单

## 8. AB-39：商品评价管理

**背景：** App 端 FR-133 改为在商品详情页**展示评价内容**（现只显示均分与条数）。

### 已确认项（2026-11-05 拍板）
