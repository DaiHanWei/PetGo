## 1. 版本目标

**把宠物身份证从"付费产物"变成"传播入口"。** 宠物身份证是全 App 视觉最完整、最有炫耀属性的产物，但它的分享入口目前埋在 HD 付费墙之后——**没付费的用户在卡面页根本找不到分享**。本版本加一个免费的分享入口（分享带水印版，无水印仍需付费），并用少量 PawCoin 激励用户去分享。

## 3. 功能与需求

### 3.1 宠物身份证分享奖励 PawCoin

**背景：** V1.1.0 FR-49 的宠物身份证（KTP / 护照 / 学生证三种卡面）已上线，卡面本身做得很完整，但**它目前不是一个拉新入口**——核实 `id_card_detail_page.dart` 后确认，该页**唯一的按钮是「解锁高清 / 下载高清」**（付费点，`id_hd_download_price`，可用 QRIS 或 PawCoin 支付），**分享动作藏在 HD 导出之后的底部选单里**（`idCardShareImage`），也就是说**没付费的用户在这个页面上根本找不到分享入口**。身份证卡面是全 App 视觉最完整、最有炫耀属性的产物，把分享入口埋在付费墙后面等于放弃了它的传播价值。本 FR 在卡面页加一个免费的分享入口，并用少量 PawCoin 激励用户去分享。

> ### ⚠️ 本 FR 与「PawCoin 任务赚取」不是同一件事，不构成那项能力的实现
>
> 项目已有一个编号保留、延期中的「PawCoin 任务赚取」能力（用户完成站内指定任务获得 PawCoin，编号 FR-50B，具体上线版本待定）。本 FR **只做一个具体动作的一次性奖励，不建任务框架**：
>
> - ❌ 不做任务列表页、不做任务进度、不做任务领取按钮、不做任务中心入口
> - ❌ 不定义可扩展的「任务 → 奖励」配置模型
> - ✅ 只在身份证卡面页加一个分享按钮，触发后按规则发一次 PawCoin
>
> **FR-50B 编号继续保留、不被本 FR 占用**；将来 FR-50B 落地时，本 FR 的这条奖励可以被它收编为其中一个任务，届时按 FR-50B 的框架重构即可，本 FR 不为此预留扩展点（预留会引入不必要的复杂度）。

#### FR-96：宠物身份证分享奖励

**入口与分享物：**

- **卡面页新增独立「分享」按钮**，与既有的「解锁高清 / 下载高清」按钮**并列展示**，**不放进 HD 导出后的底部选单里**——放进去等于仍然被付费墙挡住，本 FR 就白做了
- **分享出去的是带水印的卡面图**（复用既有水印组件 `id_card_watermark.dart`），**不是 HD 无水印图**。这是本 FR 与既有付费点共存的前提：**免费分享得到的永远是带水印版，无水印仍然只能付费解锁**
- 走系统分享菜单（`share_plus`），与 App 内既有分享动作一致；iOS 必须传 `sharePositionOrigin`（既有代码已因缺失该参数出过 iPad 崩溃与 iPhone 点了没反应的问题）
- 三种卡面（KTP / 护照 / 学生证）**均可分享**，导出画布沿用各自尺寸（既有 `_exportHd` 已按卡面类型区分画布，本 FR 复用同一套逻辑，不新写导出）
- **用户尚未创建任何身份证时**：卡面页展示的是既有的空态占位（`id_card_placeholder.dart`），**该状态下不展示分享按钮**——没有卡可分享。空态的引导动作维持现状（引导去创建），本 FR 不改动
- **总开关关闭后的按钮文案（2026-08-14 明确）**：分享按钮**仍然展示、分享功能照常可用**（分享本身有价值，不因奖励停发而砍掉入口）。因此**按钮文案本身不得包含奖励信息**——固定为「分享」而不是「分享得 N PawCoin」，奖励信息只出现在**分享成功后的轻提示**里（「+N PawCoin」）。这样总开关关闭时只需停掉那个轻提示，按钮无需切换两套文案，也不会出现"按钮承诺了奖励却不发"的失信

**奖励规则——双层控制（2026-08-14 定，取代原「每张卡只发一次」的单层设计）：**

> ### ⚠️ 为什么换设计：原方案的防刷前提被代码证伪
>
> 原方案把「**每张卡只发一次**」作为主要防刷手段，理由是「卡的数量受宠物档案数量约束，不是可无限重复的动作」。**核实 `IdCardService.createCard()` 后确认这个前提不成立**——该方法**没有任何数量限制，而且不要求有宠物档案**（代码注释原文：「卡信息与档案解耦——**不要求已有档案**，也不改档案」「每卡新号」「旧卡保留可看可下载」），表结构 `id_cards` 也只对 `serial_id` 唯一，对 `user_id` 无任何计数约束。
>
> 也就是说刷法是：**建卡 → 分享 → 拿币 → 再建一张卡 → 再分享 → 再拿币**，可无限循环，连宠物都不用养。「每张卡只发一次」挡不住任何东西。
>
> 更糟的是它**制造了一种已经防住了的错觉**，可能导致奖励值被定得过于宽松。故本次改为双层控制。

**第一层 · 全局：单账号通过所有分享类行为可免费获得的 PawCoin 月度上限**

- 定义一个**跨渠道共用**的月度上限 `SHARE_REWARD_MONTHLY_CAP`：单账号在一个自然月内，**通过所有分享类行为**累计可免费获得的 PawCoin 总量
- **本版本只有 FR-96 一个渠道消费这个额度**，但额度本身按"所有分享类行为"定义，后续新增分享渠道直接接入、不需要再造一套控制
- 自然月重置（按 WIB / GMT+7 的月初，与平台既有定时能力时区口径一致）
- 达到上限后：**分享按钮仍然正常展示、分享功能照常可用**，只是不再发放 PawCoin，也不展示「+N」提示
- `[ASSUMPTION: 达到上限时不向用户显式提示"你已达本月上限"——告知会诱导用户"攒着别分享"或在月初集中刷满，与鼓励分享的目标相悖。若上线后发现用户困惑（分享了没拿到币却不知为何），再评估是否加提示]`

**第二层 · 渠道：FR-96 自身的发放形态**

- 用户成功发起一次身份证分享 → 发放 `N` 枚 PawCoin（`N` 后台可配）
- **发放条件按「宠物档案」而非「卡」去重**（2026-08-14 修订）：**同一宠物档案的身份证，首次分享时发放一次**，之后无论该档案下再生成多少张新卡、再分享多少次，都不再发放
  - 改绑档案的理由：卡可以无限建（见上方说明），档案不行——宠物档案是有实际创建成本、且与用户真实资产绑定的对象
  - `[ASSUMPTION: 未绑定任何宠物档案的独立建卡（createCard 允许不带档案）不发放奖励——无档案的卡可无限造，是刷量的直接入口]`
- **账号级每日上限**保留为速率限制：同一账号每日通过本渠道最多获得 `M` 枚 PawCoin（`M` 后台可配），防止单日集中刷量
  - `[ASSUMPTION: M 与 N 建议配成整数倍关系（如 N=2、M=6 即每日 3 次），避免除不尽导致"还剩 1 枚额度但发不出一次完整奖励"的边界]`

**三层的关系（生效顺序，缺一不可）：**

```
① 档案首次分享？ ——否→ 不发
        ↓是
② 今日已达 M ？ ——是→ 不发
        ↓否
③ 本月已达全局上限？ ——是→ 不发
        ↓否
      发放 N 枚
```

**发放机制：**

- **每笔发放须可追溯到具体的宠物档案**，供对账与异常排查
- **发放必须幂等**：同一宠物档案无论被上报多少次**只发一次**；并发重复上报不得重复发放
- **奖励到账为即时**，前端展示一个轻提示（如「+N PawCoin」），**不做领取动作、不做动画弹层**——本版本目标是尽快上线，不为此加交互
- **发放失败不影响分享本身**：分享是本地导出 + 系统分享菜单，与奖励发放是两条独立链路。奖励写入失败时**分享照常完成**，不弹错误、不阻断；失败的发放**不做自动重试、不建补偿队列**（奖励金额很小，不值得），但幂等要求保证用户下次触发同一路径时仍可拿到

> ### ⚠️ 全局上限这一层实际上是 FR-50B 的前置能力，需要明确定性
>
> 「单账号通过各类行为免费获得 PawCoin 的总量控制」本身就是 **PawCoin 任务赚取（FR-50B，编号保留、延期中）** 的核心组件之一。本 FR 原本明确写着「不构成 FR-50B 的实现、不预留扩展点」——**第一层全局上限打破了这条定性**，必须写清楚而不是含糊过去，否则 FR-50B 真立项时会发现有一块地基已经被人按别的思路浇过了。
>
> **本版本的定性：** 全局上限是 **FR-50B 的一小块前置能力，先行交付**，但范围**严格限制在"上限控制"**——
>
> - ✅ 做：一个跨渠道的月度免费获取额度、以及额度的消费与重置
> - ❌ 不做：任务列表 / 任务进度 / 领取动作 / 任务中心入口 / 可扩展的「任务 → 奖励」配置模型
>
> **FR-50B 编号继续保留、不被本 FR 占用。** 将来 FR-50B 落地时，本层可以被它直接吸收为「免费额度总控」模块，不需要推倒重来。

**为什么是"双层"而不是只做全局上限（设计取舍，供后续复盘）：**

只做全局上限的问题是——**它管住了总量，管不住质量**。用户照样可以用无意义的分享（分享给自己、分享到剪贴板）刷满额度：额度定低了真实用户很快用完，定高了刷子也能刷满。第二层的「按档案首次去重」把奖励锚定在"用户真的多养了一只宠物/多建了一份档案"这个有成本的行为上，让额度更可能流向真实用户。**全局上限负责封顶损失，渠道规则负责提高精准度**，两者解决的不是同一个问题。

**已知未解决的：** 双层控制仍然**不能区分"真的分享出去了"和"点了分享按钮就取消"**——这是技术上的硬限制，见下方「防刷」。双层只是把损失封顶在一个可接受的量级，不是杜绝。

**⚠️ 与 HD 付费点的收入冲突（必须先定，见 OQ-A13）：**

身份证 HD 解锁**可以用 PawCoin 支付**（`IdCardHdPurchase` 渠道含 PawCoin）。因此「分享得 PawCoin」直接打通了一条**用分享换 HD 解锁**的路径——分享按钮就在这张卡上，用户分享几次就能把这张卡的付费点白嫖掉。这不是边角情况，是本 FR 的默认后果，必须显式定价：

- **约束式（必须满足，2026-08-14 按双层控制改写）**：`SHARE_REWARD_MONTHLY_CAP`（全局月度上限）应**显著低于**一次 HD 解锁所需的 PawCoin 数额
  - **注意约束的锚点变了**：原来写的是「`N ×` 可分享卡数」，但卡可以无限建、分母是无限的，那个约束式**根本不成立**。改用全局月度上限作锚点后，白嫖的天花板是确定的、可控的
  - **一句话判断标准**：看「用户攒满一个月的全局额度，够不够换一次 HD 解锁」。够 → HD 付费点每月被白嫖一次；不够 → 付费点保住
- `[ASSUMPTION: 初始取值建议全局月度上限 ≤ 一次 HD 解锁价的 1/2，即至少要攒两个月才够换一次解锁；具体数值随 OQ-A13 由产品结合当前 id_hd_download_price 定]`
- **产品也可以主动选择接受这个兑换关系**（把 HD 解锁当作分享的奖品，用收入换传播）——但这必须是**明确的决定**，不能是没注意到而默认发生的结果

**防刷（先说清楚根本限制）：**

- **「分享成功」这个信号在技术上不可验证。** 核实代码确认：App 的分享函数 `ShareFn` 返回 `Future<void>`，**连 `share_plus` 的 `ShareResult` 都没有读**；而既有的名片分享上报接口是客户端主动 POST 的、服务端不做任何校验。即使读了 `ShareResult`，它也只能告诉你用户在系统面板上选了哪个 App，**无法确认内容真的被发出去、更无法确认有人看到**
- 因此**不要试图靠"验证分享是否成功"来防刷**——做不到。本 FR 改为用**发放额度的多层上限**兜底（见上方「奖励规则」）：
  - **全局月度上限**（主要手段，封顶损失）：无论用什么方式刷，单账号每月能拿到的总量是确定的
  - **按宠物档案首次去重**（提高精准度）：把奖励锚定在有实际创建成本的对象上，而不是可无限造的卡
  - **账号级每日上限**（速率限制）：防止单日集中刷量
  - **不按分享次数计次发放**（明确排除）：那等于把奖励挂在一个不可验证、可无限重复的动作上
  - ❌ **已废弃：「每张卡只发一次」**——该手段基于"卡的数量受档案约束"这一被证伪的前提，`createCard` 无任何数量限制且不要求档案，卡可无限建。保留此条仅为留痕，防止后续有人按旧口径实现
- **异常账号交由后台监控排查，不在产品层加更多卡**：运营后台已有 PawCoin 发放/审计能力（权限码 `user.grant_pawcoin`、审计动作 `PAWCOIN_GRANTED`），本渠道的发放记录同样入账可查

**与既有「第一次分享宠物名片」信号的关系（必须区分，否则会串）：**

平台已有一个「第一次分享宠物名片」的里程碑信号（新手任务 `SHARE_CARD` / 里程碑语义后缀 S3，由 `CardSharedEvent` 驱动）。**那是宠物名片 H5（V1.0.0 FR-14），不是本 FR 的宠物身份证（V1.1.0 FR-49），两者是不同的产物。**

- 本 FR 的分享**必须发一个独立的新信号**，**不得复用 `CardSharedEvent`**——复用会导致「分享了身份证，却解锁了『第一次分享名片』里程碑」的错乱
- 反向同样：分享名片**不触发**本 FR 的 PawCoin 奖励
- **本 FR 不新增里程碑、不改动任何既有里程碑定义**

**埋点要求：** 记录分享按钮点击、奖励发放（含金额、是否因命中上限而未发放）、以及分享来源卡面类型（KTP / 护照 / 学生证）。**「点击了分享按钮」与「实际拿到奖励」必须是两个独立事件**——两者的差值就是命中上限的规模，是后续调参的唯一依据。

**Non-goal（本 FR 明确不做）：**

- **不做任务框架**（见上方说明）
- **不改动 HD 付费流程**：解锁价、支付渠道、每卡独立解锁的既有规则全部不变
- **不做分享落地页 / 分享后的回流统计**：分享出去的是一张图片，图上是否带引导码、外部点击如何回流，不在本版本范围内
- **不做分享排行榜、不做邀请关系绑定**
- **不验证分享是否真的成功**（技术上不可行，见上方）
- **不做奖励的撤回/追回**：即使事后判定为刷量，本版本不做自动扣回，交由运营按个案处理

## 4. 运营后台需求

### 4.1 AB-3M：身份证分享奖励配置（新增，对应 FR-96）

**结论先行——「写死还是配置」建议取配置，且成本极低：**

| | 写死 | **配置（建议）** |
|---|---|---|
| 首次上线成本 | 最低 | **几乎同样低**——运营后台已有配置中心（`AdminConfigService` + `ConfigType.PRICING` / `PAWCOIN`），加一组配置项 = 加字段 + 加表单项，**审计 diff、实时下发都是现成的** |
| 调参成本 | **每次调都要发版** | 后台改一下，实时生效 |
| 与项目惯例 | ❌ 相悖 | ✅ 一致——`id_hd_download_price` 已经是后台可配 + 实时下发，前端**明确不留本地兜底价**（`id_card_repository.dart` 注释记着这是修 417 类问题时确立的口径） |

**决定性理由：分享奖励是增长杠杆，上线后必然要反复调数值。** 而本版本的目标恰恰是"尽快上线"——写死意味着每调一次数值就得走一次完整发版流程，这与目标直接冲突。配置化的增量成本只有一个表单，不构成排期风险。

**配置项（挂在既有 PawCoin 配置组下，沿用其审计 diff 与实时下发机制）：**

**分两组：全局层（跨渠道共用）与渠道层（FR-96 自己的）。** 这个分组不是文档洁癖——全局层是给后续新增分享渠道复用的，混在一起配会让运营分不清"改这个数会影响哪些功能"。

**全局层（跨所有分享类行为共用，见 §3.3 第一层）：**

| 配置项 | 含义 | 备注 |
|---|---|---|
| `share_reward_monthly_cap` | 单账号每月通过**所有分享类行为**可免费获得的 PawCoin 上限 | **必须与 `id_hd_download_price` 同屏展示**，见下方护栏。**本版本只有 FR-96 消费该额度**，但定义上是跨渠道的 |
| `share_reward_enabled` | 分享奖励总开关（全局） | **必须有**——发现被刷时要能立刻全线关掉，而不是等发版 |

**渠道层（仅 FR-96）：**

| 配置项 | 含义 | 备注 |
|---|---|---|
| `id_card_share_reward` | 单次发放的 PawCoin 数（`N`） | 建议与每日上限配成整数倍关系 |
| `id_card_share_daily_cap` | 单账号每日通过**本渠道**可获得的 PawCoin 上限（`M`） | 速率限制，防单日集中刷量 |

**⚠️ 界面必须展示当前月度额度的消费情况**（本月已通过分享发放的 PawCoin 总量 / 达到上限的账号数）——否则运营改这个数就是纯拍脑袋，不知道现在卡不卡人。

**界面要求：**

- **配置页必须同屏展示当前的 HD 解锁价**，并实时算出「**攒满几个月的全局额度可换一次 HD 解锁**」这个比值提示给运营（原写"分享几张卡"，因卡可无限建、分母无限，该口径已作废）。这是本条最重要的界面要求——两个数值分开看都合理、放一起才看得出白嫖风险（同既有「装饰标签打标同时是流量动作」那类副作用明示的做法）
- 数值改动沿用配置中心既有的 diff 审计日志，可追溯改了什么、谁改的
- 总开关关闭后，App 端分享按钮**仍然展示**（分享本身是有价值的），只是不再发放奖励、不再展示「+N PawCoin」提示

**不做的：** 不做按用户分层的差异化奖励、不做限时活动倍率、不做奖励发放的后台手动补发入口（既有的 `user.grant_pawcoin` 通用发放能力已够用）。
